# Extraction, preparation and Staff receiving contract

24 October 2026. The [PRD](../product/prd.md) and [current verification](../verification/STAFF_RECEIVING_2026_10_24.md) replace the old new-receipt Manager-approval authority. Historical APPROVED records remain read-only unless Manager permanently clears Receipt history.

Manager-only extraction/matching/draft APIs retain transient images, validated allowlisted output, exact/alias matching and manual conversion. Extraction requires `ESTOCK_GEMINI_MODEL=gemini-3.8-flash`; blank or different model IDs fail configuration validation before any provider call. There is no alternate-model fallback. Google's [Gemini 3.8 Flash model documentation](https://ai.google.dev/gemini-api/docs/models/gemini-3.8-flash) lists image input and structured output support; that does not establish this account's access or measured extraction quality. New review products use Opening 0. Sending validates date, exclusions, selected active product versions and positive expected base-unit integers. A send transaction freezes `estock_receipt_submissions` + `estock_receipt_lines`, changes DRAFT to AWAITING_STAFF and inserts a deduplicated Staff notification without stock effects.

| Endpoint | Session authority | Effect |
| --- | --- | --- |
| `POST /api/estock/drafts` | Manager | Transient image → structured preparation draft |
| `GET/PATCH /api/estock/drafts/:id` | Manager | Read/save with expected revision |
| `POST /api/estock/drafts/:id/send` | Manager | Freeze validated submission; request identity; notify Staff |
| `POST /api/estock/drafts/:id/recall` | Manager | AWAITING_STAFF + expected revision → DRAFT; resolve pending notification |
| `POST /api/estock/drafts/:id/discard` | Manager | DRAFT → DISCARDED; no stock |
| `POST /api/estock/drafts/:id/approve` | Manager | Retired, 410; cannot mutate stock |
| `GET /api/estock/receiving` | Staff / Manager | Staff pending checks / Manager completed Staff receipts |
| `GET /api/estock/receiving/:id` | Staff / Manager | Frozen checking details; Staff cannot read general drafts or recalled checks |
| `POST /api/estock/receiving/:id/confirm` | Staff only | Physical declaration; actual quantities and stock post atomically |
| `GET /api/estock/notifications` | Either | Session-role scoped notifications and unread count |
| `DELETE /api/estock/notifications` | Either | Exact `confirmation: "Clear Notifications"`; permanently delete that session account's notifications, retaining pending checks |
| `POST /api/estock/notifications/:id/read` | Owning role | Persist read state only |
| `DELETE /api/estock/history/receipts` | Manager | Require JSON `confirmation: "Clear History"` exactly; permanently remove completed/discarded receipt records and notifications; retain detached stock ledger |
| `DELETE /api/estock/history/activity` | Manager | Exact `confirmation: "Clear Stock Activity"`; permanently remove activity details, retain aggregate stock balance and retry identities |

Confirmation requires requestId, expectedRevision, confirmReceived=true and exactly every included submitted line ID with `actualQuantity`, a nonnegative safe integer. The server compares it with each locked frozen expected quantity to derive MATCH/SHORT/EXTRA and the difference. Older clients may still submit an all-legacy outcome/difference payload; ambiguous mixed fields/formats are rejected. Actual quantity may be zero, cannot be negative/fractional/unsafe. Foreign/excluded/duplicate IDs and stale versions fail. Client quantities do not directly set balances. Expected values and extracted fields remain separate from actual results. Staff sees one editable actual-count field per product, initially filled with expected, without manually selecting Short or Extra.

`receiving.ts` locks the receipt then all selected products in sorted ID order. It commits line outcomes, check identity, positive actual Intake, product balances, receipt completion, Staff notification resolution and required Manager discrepancy notice together. `estock_receipt_checks` has one row per draft; movements retain unique `intake:<line ID>` identity. Request keys use persisted fingerprints/results. Same-key replay returns the committed result; different keys cannot repost the receipt. Zero actual creates no movement, but keeps the line/check/completed receipt. Matching deliveries create no Manager discrepancy alert.

A deleted product blocks the entire check. Manager uses Recall to correct, selects an active replacement (or valid exclusion), saves and sends a new revision. Existing immutable submissions remain evidence. Races among recall/check/archive serialize on rows; never post to a hidden product. Catalog renames do not alter the submitted name/unit snapshot. Historical receipts use their original ledger snapshots.

Document date is separate from Manager sent time, shared Staff checked time and posting time. Only historical APPROVED rows have Manager approval attribution. New History is sourced from receipt/check records, including zero-Intake deliveries, rather than assuming every completed receipt has a movement.

Polling runs every eight seconds and on window focus, with an in-flight guard and cleanup/abort. A displayed Staff submission and entered actual counts stay fixed across polling: a new revision disables confirmation until Staff explicitly uses Reopen latest check, resetting counts to the latest expected quantities. Notification reads never alter inventory. No external messaging service exists.

Application images are not retained: saved drafts contain structured fields only. Extraction uses one SDK attempt per operation, with at most one additional operation after numeric provider HTTP 503, and no 45-second application deadline; upstream, network and hosting time limits still apply. A slow scan stays pending in the UI. Any supported supplier document can be submitted; local example photos guide the prompt and do not whitelist documents or train model weights. Extracted issue dates prefill the editable date field; the server still stores the candidate separately until Manager saves or sends. Positive whole-number quantities prefill Expected quantity, including unmatched lines; fractional/unreadable quantities remain blank. Manager checks source units and any uncertain lines before sending. Extraction is outside stock transactions. No monetary data or document instructions can grant stock authority. A small exploratory live OCR sample using synthetic documents exists, but broad provider accuracy/retention, physical capture and hosted durability remain unverified; see [earlier QC](../verification/END_TO_END_QC_2026_10_24.md).

Manager Clear history deletes terminal RECEIVED, DISCARDED and historical APPROVED draft/receipt rows, exclusion snapshots, notifications and matching send/confirm/legacy-approve replay results in one transaction. Intake movements keep product, amount, actor, time and balance but lose bon fields and draft/line references. Active DRAFT/AWAITING_STAFF records and Stock activity remain. Clearing removes the old receipt evidence used for duplicate-document warnings; this is permanent and is never executed automatically.

Migrations: `db/estock/migrate.mjs` is shared by `ready()` and `scripts/estock-migrate.mjs`; ordered numbered SQL files run once per schema under transaction/advisory lock. Existing unversioned 001 schemas are adopted via idempotent 001, then additive 002–005. Migration 004 freezes reviewed names and exclusion reasons for new sent revisions; historical excluded-line snapshots cannot be reconstructed. Migration 005 adds carried-forward activity balances and an Opening claim guard, without clearing data. Never edit only CREATE definitions or reset volumes. See [README](../../README.md).
