# Inventory, archive and movement contract

## Inventory management and permanent deletion

Draft product matching now uses one active catalogue/alias snapshot per draft operation. The shared ranker folds spelling format and scores character/token similarity; a unique exact candidate or strong >=0.90 match with >=0.08 lead can prefill. Numeric order and recognized unit/colour attributes must agree; ambiguity stays blank. New drafts persist ID/version. Older unmapped drafts expose suggestedProductId without mutating GET data; frontend Save/Send persists that prefill before submission. Existing manual selections remain authoritative. These heuristics are not a guarantee that every visually similar name identifies the same physical product.

Manager opens **Manage products** from Inventory for Edit/Delete. Inventory rows expose only Take/Return. Single-product Delete retains the archive behavior below.

Manager `DELETE /api/estock/products` separately requires exact `confirmation: "Delete All Inventory"` and a persistent requestId. The UI supplies this token after explicit click confirmation, without asking the user to type it. It permanently removes all active/archived products, balances and confirmed aliases in one transaction. Draft-first exclusive table locks serialize catalogue writes and receipt confirmation. Active mappings lose their product/version/alias selection and their draft revision changes; pending submissions return to DRAFT with resolved Staff notifications. Previously loaded Staff checks fail closed. Product-operation and recalled-Send replay payloads are tombstoned (410 INVENTORY_DELETED); the deletion request itself replays its original result without deleting later-created products.

Migration 006 uses nullable, ON DELETE SET NULL product references in movements, receipt snapshots and draft lines, and ON DELETE CASCADE for aliases and carried balances. Historical names/units/quantities and receipt outcomes remain until their separate Clear action. Old detached activity remains clearable. Product deletion creates no artificial Take/adjustment. Individual product archive and permanent bulk deletion are intentionally different actions. [47-test and browser evidence](../verification/INVENTORY_MANAGEMENT_2026_10_24.md).

Product balance = Opening + Intake − Take + usable Return. Opening is a once-only nonnegative integer recorded atomically at Manager creation; receipt-preparation product creation uses 0. Intake/Take/Return are positive safe integers in one immutable base unit. Zero actual receiving is retained in check/history and creates no movement. Generic movement APIs accept only Take/Return, never direct Intake.

Manager may permanently clear Stock activity with exact JSON confirmation `Clear Stock Activity` at `DELETE /api/estock/history/activity`. The transaction locks affected products in ID order, adds removed Opening/Take/Return deltas into `estock_activity_balances`, replaces the corresponding TAKE/RETURN/CREATE_PRODUCT replay results with a minimal `activityCleared` marker, and deletes the individual activity movements. Product stock, catalogue and Intake/receipt evidence are unchanged. Request IDs, action/role and fingerprints remain; exact old retries return 410 ACTIVITY_CLEARED, and changed-payload reuse still conflicts. Later activity remains usable and can be cleared again. Reconciliation after a clear is product stock = sum of surviving movement deltas + carried-forward activity delta. That numerical aggregate has no original event times, actors or per-event quantities. `opening_recorded` plus the migration-005 trigger enforce once-only Opening even after its history row has been removed.

Inventory/search/matching/counts/Low stock use active products only. Low stock is strictly below 5, including zero. Official-name/alias search is case insensitive, with explicit Manager matching for ambiguity; no automatic package conversions. Catalogue name edits increment product version but cannot rewrite stock, units or historical snapshots.

Both roles Take/Return. Take dialog shows available stock, preserves empty intermediate editing, marks excessive typed/pasted quantities invalid and disables submission, while native max bounds stepper. Backend locks the product and rejects quantity > current stock. An insufficient-stock conflict triggers dialog availability refresh; concurrent Take cannot go negative. Return has no current-stock cap and no prior-Take/refund linkage. Both mutations persist request identity and input fingerprint inside the stock transaction; replay is safe and changed-payload reuse conflicts. Actors derive from server sessions and identify shared Staff honestly.

Manager `DELETE /api/estock/products/:id` requires expectedVersion + requestId. Under the same product lock used for stock movements, it sets archived_at/by and archived_stock=stock, increments version and retains the entire row/ledger/references. No stock clearing or fabricated movement. Manager UI has exactly one native modal confirmation with product name/current stock, Cancel/Delete and retained-history explanation. Busy/error states prevent duplicate submission. Staff server deletion is denied. Archived products cannot be edited, used in Take/Return or new matching and never reactivate automatically.

If archive wins a receiving race, the complete receipt check rolls back with ARCHIVED_PRODUCT; Manager recalls/corrects/resends. If receiving wins, archive retains the resulting balance snapshot. Receipt-level once-only protection is separate from per-request identity. All inventory writes preserve ledger reconciliation, including archived remaining balances.

Full History remains Manager-only. Primary Receipt history includes completed and discarded receipts, frozen expected/actual details and all-missing deliveries, server Manager preparation/shared Staff confirmation/posting times and separate original document date. Historical Manager-approved receipts preserve original actors/times until Manager uses Clear history. That action permanently deletes terminal receipt evidence and notifications while detaching its metadata from Intake movements; stock balances and minimal movement ledger remain. Active drafts and pending checks are unaffected. Stock activity separately shows Take/Return and labelled Manager Opening; product archive never deletes it.

Explicit setup and app startup share versioned transactional migrations. The retained isolated PostgreSQL tests exercise fresh and populated upgrades, permissions, bounds, races, injected rollback, missing goods, notifications and reconciliation.
